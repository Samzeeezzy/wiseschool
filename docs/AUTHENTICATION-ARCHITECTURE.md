# WISE Authentication & Account Provisioning Architecture

## Approved policy decisions

These decisions are approved for the WISE platform:

1. **All user categories** must authenticate with Google and complete WISE school verification before first account activation: administrators, teachers, non-teaching staff, students and parents/guardians.
2. **Only the Super Administrator** may generate, issue, revoke or reissue WISE verification codes.
3. **Parent/guardian verification is admission-record based.** A parent must identify the relevant student's admission record and prove that the school has authorised that adult as the student's parent/guardian. An admission number by itself is not proof of guardianship and must never grant access.
4. A verification code is a one-time account-enrolment credential. It is not the user's Google password and is not normally requested on every sign-in.

## User journey

### First-time activation

1. User chooses the correct account category and selects **Continue with Google**.
2. The backend completes Google OAuth 2.0 Authorization Code flow. It validates the returned ID token server-side: signature, issuer, audience/client ID, expiry and nonce/state. Require Google's `email_verified` claim.
3. The user submits the WISE verification information for their category.
4. The backend checks the matching pre-provisioned school record, code hash, intended category, expiry, revocation/consumption state and any required identity match.
5. In one database transaction, the backend consumes the code, links the Google subject (`sub`) to the existing school record, creates/activates the account and assigns only the role pre-authorised by the school.
6. The user receives a server-side session and is redirected to the permitted portal.

If any check fails, no account is activated and no role is granted. Do not reveal whether a particular student, employee, parent or admission record exists in public error messages.

### Returning sign-in

1. User signs in with Google.
2. Backend validates the OAuth response and finds the already-linked Google subject.
3. Backend checks that the account is active and not suspended/revoked.
4. Backend creates a fresh secure session and loads permissions from the database.
5. A new verification code is not requested for every ordinary sign-in. Require re-verification for account recovery, a changed Google identity, a risk-triggered event or an administrator-directed reset.

## Category-specific enrolment

### Administrators and employees

- Super Administrator pre-creates or verifies the employee record and chooses the permitted role.
- Super Administrator generates a random, high-entropy, single-use code tied to that exact staff record and category.
- Deliver the code privately to the employee using a school-approved channel. Do not display it again after issuance.
- Employee completes Google sign-in and submits the code. The Google email should match the staff email held by the school, unless an authorised exception is recorded and approved.
- The employee cannot self-select or elevate their role.

### Students

- School record must already exist and be active.
- Super Administrator generates a code tied to the student's existing record and student category.
- Student signs in with their own Google account and submits the code plus the school identifier requested by the portal (for example, admission number).
- The admission number is a lookup value, not a secret and not sufficient on its own to activate an account.
- For younger students without an appropriate individual Google account, WISE must define a school-approved access arrangement before enabling student Google accounts. Do not silently share a parent's Google identity as a student's identity.

### Parents and guardians — admission-based verification

- A parent begins with Google sign-in and selects **Parent/Guardian**.
- Parent supplies the student's admission number/reference and the school-issued parent verification code.
- The backend finds the admission/student record and checks a pre-existing parent/guardian relationship or a school-approved pending guardian record.
- The code is generated by the Super Administrator and bound to the intended guardian, the relevant student/admission record, the parent category and (where applicable) a specific Google email.
- If the parent is not already recorded, the registration remains pending until the school verifies the adult and adds/approves the guardian relationship. Admission number alone must never create a guardian link.
- After approval, create a row in the parent-student relationship table with relationship type and status. A parent can see only children linked to that parent account and authorised by the school.
- For siblings, create separate approved links for each child; do not infer sibling relationships from matching surnames or contact details.

## Super Administrator code management

Only an active Super Administrator permission may access code management. Provide:

- Generate a cryptographically random, single-use code.
- Select an existing school record and fixed category; do not allow arbitrary role assignment.
- Bind the code to the intended record and optionally the exact verified Google email.
- Set a short expiry window and maximum failed attempts.
- View status metadata (issued, redeemed, expired, revoked) without ever revealing stored code values.
- Revoke or reissue a code; reissue invalidates the previous code.
- Record issuer, intended recipient/record, category, issue time, expiry, redemption time and revocation reason in the audit log.
- Bulk generation may be supported, but each code must be unique and individually bound.

## Suggested MySQL schema

Use InnoDB, foreign keys, UTC timestamps and appropriate unique constraints. Adapt names to the final schema migration conventions.

### `users`
- `id` (primary key)
- `google_sub` (unique, not nullable after activation)
- `email`, `email_verified`, `display_name`
- `status` (pending, active, suspended, disabled)
- `created_at`, `last_login_at`

### `school_people`
A common identity/provisioning record for an existing staff member or student; alternatively retain existing staff/student tables and reference them polymorphically through a dedicated enrolment table.
- `id`, `person_type` (staff or student), `staff_id` nullable, `student_id` nullable
- `expected_email` nullable, `status`
- Enforce exactly one valid staff/student reference and uniqueness.

### `roles` and `user_roles`
- Define controlled roles: super_admin, school_admin, teacher, non_teaching_staff, student, parent.
- `user_roles` maps a user to an approved role and optional scope (class, subject, campus).
- Never accept role names or permissions supplied by the browser as authority.

### `verification_codes`
- `id`, `code_hash` (unique), `category`, `target_person_id` / `target_guardian_id`
- `expected_google_email` nullable
- `expires_at`, `max_attempts`, `attempt_count`
- `issued_by_user_id`, `issued_at`, `redeemed_at`, `revoked_at`
- Store only a keyed hash or secure password hash of the code; never store plaintext.
- Index code hash, target, category and expiry. Never log the raw code.

### `guardians` and `parent_student_links`
- Guardian record contains verified adult identity/contact information.
- Relationship table contains `guardian_id`, `student_id`, `relationship_type`, `status`, `approved_by_user_id`, `approved_at`.
- Enforce that portal queries scope every child record through an active parent-student link.

### `audit_logs` and `login_logs`
Record security-relevant events without passwords, OAuth tokens, raw codes or unnecessary sensitive data.

## Security requirements

- Use HTTPS only; keep Google client secret, database credentials and application secrets outside the public web root and out of Git.
- Use OAuth state and nonce, PKCE where supported, strict redirect URI allowlists and server-side token validation.
- Store Google `sub` as the durable identity key; email is an attribute and may change.
- Generate codes with a cryptographically secure random generator; use sufficient entropy, one-time redemption, expiry, rate limits and lockout/backoff.
- Store code hashes only. Compare safely and consume atomically in a database transaction to prevent race/replay attacks.
- Generic public error messages; detailed reason only in protected server logs.
- Use PHP prepared statements, output escaping, CSRF protection, secure/HttpOnly/SameSite cookies, session ID rotation after authentication and idle/absolute session expiry.
- Enforce role and record-level authorization on every backend request. Hiding buttons in the browser is not authorization.
- Protect parent/guardian data and child records with explicit relationship checks on every request.
- Require MFA for Super Administrator accounts where available; maintain at least two named, school-controlled emergency administrators with documented recovery procedures.
- Log code issue/revoke/redeem, role changes, guardian approvals, account suspension and sensitive record access.
- Back up and test restoration. Apply data minimisation, retention and school-approved privacy/consent procedures.

## cPanel deployment configuration

- PHP backend and MySQL/MariaDB database on the school's cPanel hosting.
- Use a supported PHP version, PDO MySQL, HTTPS and server-side environment/configuration outside `public_html`.
- Create separate development/staging and production databases where the hosting plan permits.
- Configure Google OAuth authorized origins and exact redirect URI only after the production/staging domains are known.
- Do not commit `.env`, OAuth client secrets, database passwords, production exports or real student/guardian data.
- Use schema migrations and a least-privilege database user. phpMyAdmin is for authorised database administration, not a public application interface.

## Dependencies and go-live gates

Before implementing live OAuth and account activation, obtain:
- School-owned cPanel host/domain and PHP/MySQL version details.
- A school-controlled Google Cloud project and OAuth consent configuration.
- Named Super Administrator accounts and recovery/MFA policy.
- Verified staff/student records and guardian/admission relationships, imported securely.
- Approved code delivery method and identity-check procedure for parents/guardians.
- Privacy notice, consent/retention rules and approved onboarding instructions.

Until these are available, implement the schema, backend interfaces and test fixtures only. Do not create fake live users, hardcode shared secret codes, or activate real accounts using public admission numbers.
